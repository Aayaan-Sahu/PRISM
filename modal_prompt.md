I am building a real-time, multi-speaker biometric voice recognition system in Python. It acts as a "smart noise gate"—when an enrolled target speaks, it tracks their voice; when an unenrolled person speaks, it mutes them. 

### How the Current System Works:
1. **Local Enrollment**: A script (`enroll_target.py`) records 5 seconds of audio for any number of users and saves a 192-dimensional SpeechBrain ECAPA-TDNN feature embedding as `{name}.npy` inside an `embeddings/` folder.
2. **Local VAD Pipeline**: A streaming script (`target_speaker_vad.py`) reads a single microphone channel using `sounddevice` (mono audio). It runs computationally cheap STFT spectral subtraction in real-time. It continually updates an Exponential Moving Average (EMA) of the background frequency profile. When someone speaks, a secondary thread runs PyTorch broadcast math against the $N \times 192$ multi-speaker embeddings. If the `cosine_similarity` breaches `0.3`, it freezes the background profile update, opens the gain gate, and passes the audio through.

### The Problems with the Current Approach:
1. **The Double Talk Mono Limitation**: Because we rely on single-channel STFT frequency subtraction, if an enrolled Target is talking (the gate is open and background profiling is frozen), and an unenrolled friend immediately interrupts and talks over them, the system cannot mathematically separate the frequencies. It simply amplifies both people because they overlap on the single mic. 
2. **Compute Latency**: We want to fix the single-mic overlap limitation by replacing rudimentary STFT math with true Deep Learning Source Separation (i.e., feeding the mixed audio into an AI that spits out two separate clean voice tracks). However, running `speechbrain/sepformer-wham16k-enhancement` locally on a Mac M4 takes `~2.17s` to process 5 seconds of audio. This is far too slow for real-time conversation.

### The Solution: Cloud AI Source Separation
I want to move the heavy lifting to the cloud using **Modal** and an **NVIDIA H100 GPU** to act as our intelligent "un-mixer" and gatekeeper.

Please write the code for the following updated architecture:
1. **Modal Backend (`modal_separator.py`)**: Create a FastAPI WebSocket endpoint deployed on Modal. It should hold the `speechbrain/sepformer-wham16k-enhancement` model and the `ECAPA-TDNN` model in active VRAM. Upon connection, it should receive our $N \times 192$ embedding matrix.
2. **WebSocket Streaming**: Write the local Mac client that continuously streams small chunks (e.g., `150ms`) of `bytes` audio generated by the microphone up to the `wss://` WebSocket connection. 
3. **Separation and Routing**: As the chunks hit the Modal GPU, the `sepformer` model should separate the single noisy channel into $X$ clean audio voice tracks. The Modal GPU then runs the ECAPA `cosine_similarity` check on each clean track against the loaded embeddings.
4. **Return**: The API should evaluate which tracks breached the biometric distance threshold and which belong to unenrolled speakers, and stream the resulting modified `bytes` straight back down the WebSocket to the Mac for instantaneous `sounddevice` playback.

### Critical Hackathon Demo Considerations
For the "Return" step (step 4), I want you to evaluate a design tradeoff before writing the full implementation: 
**When NO enrolled Target users are speaking, should we completely silence the unenrolled speakers/background noise, or should we just heavily dim/suppress their volume?** 
Both outcomes would be really cool for our hackathon demo. Removing them completely is slightly cooler and more ideal, but if it is harder to achieve flawlessly or causes audio glitches/artifacts when the source separation model struggles slightly, we shouldn't push for it. Please evaluate this tradeoff considering:
1. **Latency**: Which approach adds less overhead to the WebSocket loop?
2. **Feasibility**: How difficult is it to confidently drop a separated track vs just mixing it back in with a `{0.1}` gain multiplier?
3. **Consistent Accuracy**: We have to stand in front of judges and demo this live multiple times. Which approach is more robust against edge cases (like `sepformer` making a small mistake tracking the voices) without creating jarring, robotic audio cutouts?

Choose the safest, most "demo-able" approach for a hackathon, and implement the code based on that choice. Focus heavily on keeping the async WebSocket loops as fast and tightly coupled as possible to minimize latency.
